# Lessons

## 2026-09-22 展示專案裡的「魔術數字」不可信

**失敗模式**：把既有程式碼裡的常數當成正確答案寫進測試期望值。
本專案前端與 seed 到處寫死月付金 14982，實際 50萬/4.88%/36期 的年金公式值為 14958.52。

**偵測訊號**：先寫下「以既有常數為期望值」的測試，測試立刻失敗 —— 失敗指向的是常數錯、不是實作錯。

**預防規則**：展示／原型專案的數值常數預設視為未驗證。為金融計算寫測試時，
期望值一律獨立推導（手算或另一套工具驗算），不從被測程式碼或其呼叫端抄。

## 2026-09-22 additive migration 讓既有列成為 NULL 地雷

**失敗模式**：為向後相容把新的 `user_id` 設為 nullable，但 Go 端以 `string` scan，
導致認證上線前建立的舊列讓整份清單查詢回 500。有過濾條件的查詢正常，
沒過濾的查詢才炸 —— 因此單看其中一支端點會誤判功能正常。

**偵測訊號**：同一組 scan 邏輯，一支端點 200、另一支 500。

**預防規則**：
1. `ALTER TABLE ADD COLUMN` 未帶 NOT NULL 時，Go 端接收型別一律用指標或 `sql.Null*`。
2. 欄位語意上「必須有值」但結構上可為 NULL 時，要明確定義舊列的業務處理方式
   （此處：孤兒申請不得核准成合約），不能只讓它靜默通過。
3. 端到端腳本要涵蓋「不帶過濾條件」的列表端點，才會踩到殘留舊資料。

## 2026-09-22 金流冪等要靠資料庫約束，不能只靠狀態判斷

**失敗模式（預防性）**：實作還款時，直覺做法是「先讀期數狀態，若非 paid 就扣款並更新」。
這在併發下會漏：兩個請求同時通過狀態檢查，各自寫入一筆扣款。

**預防規則**：任何「只能發生一次」的金流動作都要有一個能表達該意圖的冪等鍵，
並在資料庫加唯一約束（此處 `repayments.idempotency_key`）。
狀態檢查保留作為快速路徑與可讀錯誤訊息，但**正確性由約束保證**，不由檢查保證。

驗證方式：測試必須包含「重送同一請求」並斷言第二次回 409 且紀錄只有一筆
（verify-flow.sh 第 12 節）。

## 2026-09-22 日期判定不要用應用伺服器時間

**失敗模式（預防性）**：逾期天數若用 Go 的 `time.Now()` 與 DB 的 `due_date` 相減，
容器時區設定與資料庫時區不一致時會產生 off-by-one，且難以重現。

**預防規則**：涉及「今天是哪一天」的業務判定一律在 SQL 內用 `CURRENT_DATE`，
純函式版本（`overdueDaysBetween`）只用於單元測試與顯示層，兩者都先截斷到日。

**Tripwire**：測試包含「同一天不同時刻結果必須一致」
（`TestOverdueDaysIgnoresTimeOfDay`）與「繳款日當天不算逾期」兩條斷言。

## 2026-09-22 新增環境變數不會自動進入既有 runtime env

**失敗模式**：`prepare_env_file()` 只在 runtime env 不存在時才從 `.example` 複製。
既有環境部署新版時，新增到 `.example` 的鍵永遠不會出現在 runtime env，
程式以預設值靜默啟動（或如本次，因缺金鑰而啟動失敗）。

**偵測訊號**：新版程式讀不到剛加的環境變數；`grep KEY docker/envs/.env.<env>` 找不到，
但 `.example` 裡明明有。

**預防規則**：env 樣板與 runtime env 之間要有同步機制（已加 `sync_env_with_example`），
補入新鍵但保留既有值。加環境變數時一併確認：compose 有傳遞、樣板有記載、同步會補入。

## 2026-09-22 啟動期的資料搬遷不可假設 schema 已就緒

**失敗模式**：把需要應用層邏輯的資料搬遷（此處為 PII 加密，SQL 無法完成）放進 API 啟動流程，
但 `deploy.sh` 是「先啟容器、後跑 migration」，導致搬遷找不到欄位，
API 因 `os.Exit(1)` 進入重啟迴圈，migration 永遠等不到健康的 API。

**預防規則**：
1. 啟動期任務若依賴 migration 建立的結構，必須先檢查結構是否存在
   （`information_schema.columns`），未就緒時記錄並跳過，**不可讓程序退出**。
2. 部署腳本要在 migration 後重啟應用，讓這類任務在同一次部署內完成。
3. 一次性資料搬遷失敗不應阻止服務啟動 —— 它不影響新資料的正確路徑。

## 2026-09-22 Proxy 是 header 的瓶頸，預設會丟失

**失敗模式**：Nuxt proxy 以 allowlist 轉發 header。後端正確回了 `Retry-After`，
但 proxy 沒轉發，客戶端收到 429 卻不知何時可重試。
同一個 allowlist 先前也漏掉 `cookie`（讓認證完全失效）與 `x-csrf-token`。

**預防規則**：每次在後端新增有語意的 request/response header，
必須同步檢查 proxy 的雙向 allowlist。
**Tripwire**：verify-flow.sh 對 429 斷言 `Retry-After` 存在，對登入斷言 cookie 已下發。

## 2026-09-22 CI 設定檔要在提交前做語法驗證

**失敗模式**：手寫 `.github/workflows/ci.yml` 時把 `steps:` 打成 `steps`（缺冒號）。
這種錯誤在本機不會被任何工具發現，要等 push 後 CI 報錯才知道。

**預防規則**：寫完任何 YAML 設定檔（workflow、compose）立刻用解析器驗證：
`python3 -c "import yaml; yaml.safe_load(open('path'))"`。
Compose 檔另可用 `docker compose config --quiet`。

## 2026-09-22 「會跳過」的測試需要一道確認它真的跑了

**失敗模式（預防性）**：整合測試設計成「連不到 DB 就跳過而非失敗」，
讓沒有 DB 的環境仍能跑單元測試。但這也意味著 CI 若因連線字串錯誤而連不上 DB，
測試會靜默跳過、CI 顯示綠燈，實際上什麼都沒驗證。

**預防規則**：任何有「條件跳過」機制的測試，CI 必須額外加一步斷言它確實執行
（grep 輸出中的 PASS 紀錄，並偵測 "skipped" 字樣）。
跳過是給開發者的便利，不是給 CI 的。

## 2026-09-22 SSR 的 fetch 不會自動帶瀏覽器 cookie

**失敗模式**：把認證檢查放進路由守衛後，已登入的使用者存取 `/dashboard` 仍被導向登入頁。
原因是守衛在 SSR 階段執行，`$fetch('/api/v1/auth/me')` 是從伺服器發出的新請求，
不帶瀏覽器的 cookie，因此伺服器端一律視為未登入。

**偵測訊號**：API 直接呼叫（帶 cookie）回傳正確使用者，但頁面卻被導走；
`curl -b cookies /dashboard` 回 302。

**預防規則**：需要認證的資料讀取一律走統一的 helper
（此處 `composables/useApiFetch.ts`），在 SSR 時以 `useRequestHeaders(['cookie'])` 轉發。
不要在每個呼叫點各自處理——五個 composable 都需要，漏一個就是一個 bug。
變更狀態的請求只在 client 執行，不受影響。

## 2026-09-22 友善的錯誤畫面不等於正確的狀態碼

**失敗模式**：`/repay/<不存在的id>` 顯示「找不到這份合約」的友善訊息，
但 HTTP 回 200。監控、爬蟲與 uptime 檢查都會把它當成正常頁面。

**預防規則**：SSR 頁面在資料取不到時，除了顯示訊息，也要用
`setResponseStatus(useRequestEvent(), 404)` 設定狀態碼。
注意 `useRequestEvent()` 只在 SSR 有值，client 端需以 `import.meta.server` 守衛。

## 2026-09-22 env 同步只補新鍵，不會更新既有鍵的值

**失敗模式**：我為了讓端到端腳本能連續重跑，把 `.example` 的
`AUTH_RATE_LIMIT_PER_MINUTE` 從 10 調到 20、再到 60，每次都重新部署，
但腳本持續因 429 失敗。花了很久懷疑腳本設計、等待邏輯、XFF 偽造，
最後才發現 runtime env（`docker/envs/.env.develop`）的值**始終是最初的 10** ——
`sync_env_with_example` 是我自己寫的，它只補「不存在的鍵」，不更新既有鍵的值。

**偵測訊號**：改了設定、重新部署，行為卻完全沒變。

**預防規則**：改環境變數的預設值後，第一件事是確認 runtime env 的實際值
（`grep KEY docker/envs/.env.<env>`），而不是假設部署會同步。
只補新鍵是刻意的設計（不覆蓋使用者自訂值），但這代表**改預設值需要手動更新 runtime env**。
排查「設定改了卻沒效果」時，先驗證值真的到達了程式，再懷疑邏輯。

## 2026-09-22 反向代理會讓 IP 限流失效

**失敗模式**：限流依來源 IP 計數，但所有請求都經由 Nuxt proxy，
proxy 的 header allowlist 不含 `x-forwarded-for`，因此後端看到的永遠是
proxy 容器的 IP —— **所有使用者共用一份配額**。

我一度試圖用偽造的 `X-Forwarded-For` 隔離測試配額，那當然無效
（header 根本沒被轉發，且後端刻意取最後一跳以防偽造）。

**預防規則**：
1. 在代理後方做 IP 限流時，代理必須把真實對端位址附加在 XFF 鏈尾，
   後端取最後一跳（客戶端偽造的前綴會被忽略）。
2. 部署文件要說明這件事——配額數值的意義完全取決於代理是否正確轉發。
3. 測試限流時不要嘗試偽造來源；改為讓測試可選（opt-in），
   或在測試環境調低配額。

## 2026-09-22 具名 volume 的權限來自映像中的掛載點

**失敗模式**：API 以 `nobody` 執行，掛上 docker 具名 volume 後上傳一律 500。
原因是映像中不存在 `/var/lib/creditflow/documents`，Docker 便以 root、權限 755
建立該路徑，非 root 程序寫不進去。

**偵測訊號**：容器內 `ls -ld <掛載點>` 顯示 `root root`，而 `id` 顯示非 root。

**預防規則**：任何要讓非 root 程序寫入的 volume 掛載點，
必須在 Dockerfile 中先 `mkdir` 並 `chown` 給執行身分。
Docker 會沿用映像中該路徑的擁有者與權限；路徑不存在時才退回 root。
修好後需 `docker volume rm` 既有的 volume，否則舊的權限會留著。

## 2026-09-22 HTTP 標頭只能放 ASCII

**失敗模式**：把中文檔名直接寫進 `Content-Disposition: attachment; filename="測試文件.pdf"`，
下載時檔名變成 `,f��.pdf`。

**預防規則**：非 ASCII 檔名依 RFC 6266／5987 同時提供兩種形式：
`filename=`（ASCII fallback，非 ASCII 字元換成底線）與
`filename*=UTF-8''<百分比編碼>`（現代瀏覽器優先採用）。
**Tripwire**：測試斷言標頭全為 ASCII、不含 CR/LF、且含 `filename*=UTF-8''`。

## 2026-09-22 Proxy 的 body 與回應處理要依 content-type 分流

**失敗模式（延續先前的 proxy 教訓）**：Nuxt proxy 對所有請求呼叫 `readBody`，
這會解析並破壞 multipart 的邊界字串；回應一律當 JSON 解析也會破壞二進位下載。

**預防規則**：proxy 對 `multipart/form-data` 用 `readRawBody(event, false)` 原樣轉發，
對二進位回應設 `responseType: 'arrayBuffer'` 並回傳 Buffer，
同時轉發 `content-type`、`content-disposition`、`content-length`。
這是同一個 proxy 的第四個 header/body 相關缺陷（cookie、CSRF、Retry-After、XFF、multipart）——
**每次在後端新增有語意的 header 或非 JSON 內容型別，都要回頭檢查 proxy**。

## 2026-09-23 邊界元件用排除清單，不用 allowlist

**失敗模式**：Nuxt API proxy 以 allowlist 逐項轉發 header 與內容型別。
同一支檔案因此造成**五次**靜默失效：cookie（認證全毀）、`x-csrf-token`（防護無法使用）、
`retry-after`（429 資訊丟失）、`x-forwarded-for`（限流失效）、
multipart（上傳與二進位下載都壞）。每次都是後端新增了有語意的東西，
proxy 不知道要轉發它——而且都是**靜默**失敗，沒有錯誤訊息。

**根本原因**：allowlist 把「新增功能」和「修改邊界元件」綁在一起。
只要有人忘了第二步，功能就默默壞掉。

**預防規則**：轉發性質的元件（proxy、序列化、事件轉送）一律採
「預設全部通過、明確排除少數」。排除的項目通常是協定層面的固定集合
（hop-by-hop header、由傳輸層重算的欄位），不會隨業務功能增加。

**Tripwire**：端到端驗證要有一節鎖住透通性——後端新增的 header 必須能穿透。
驗證方式是在後端暫時加一個全新 header，確認未改 proxy 也能到達客戶端。

**連帶原則**：避免以路徑字串判斷行為（`path.includes('/download')`）。
改用內容本身回報的資訊（回應的 `content-type`），新端點才不會踩雷。

## 2026-09-23 「重跑所有 migration」會讓舊檔案必須預知未來

**失敗模式**：`migrate.sh` 每次部署都重跑所有 `*.sql`。因此當 005 為
`applications.status` 加入 `funding` 等值後，002 的 CHECK 約束也必須含有這些值——
否則重跑 002 時會被既有資料列違反，部署直接失敗（已實際發生）。

同一支 migration 因此同時描述兩個時間點的 schema，歷史紀錄失去意義。

**預防規則**：migration 必須有版本表，每支只套用一次。
版本表要記 checksum 並在不符時失敗——已套用的 migration 被改動代表各環境已分歧。
既有環境導入版本表時需要 bootstrap（偵測既有 schema 並標記為已套用，不重跑）。

**連帶注意**：「migration 都是 idempotent」這個前提只對擴張型變更成立。
收斂型變更（CHECK 改窄、加 NOT NULL、加唯一約束）無法對已含不符資料的 DB 重複套用。
因此測試若要重跑全部 migration，必須先重建 schema（`DROP SCHEMA public CASCADE`），
而不是假設可以疊加套用。

## 2026-09-23 自己設的守衛擋住自己時，先查證再決定

**情境**：我加了 checksum 守衛（已套用的 migration 不可修改），
接著要修的第一件事就是 002——立刻被自己的守衛擋下。

**做法**：先查資料庫的實際約束定義，確認 002 的修改是純文件性質
（實際約束已由 005 加寬，與 002 的檔案內容無關），才手動更新記錄的 checksum。

**規則**：守衛擋住時不要直接關掉或加例外開關。先確認「被擋的這件事到底安不安全」，
安全就明確記錄理由後繞過一次，不安全就照守衛說的做。
守衛的價值在於強迫這個查證動作發生。

## 2026-09-23 「加密」不一定是敏感欄位的正解

**情境**：待辦寫的是「`annual_income` 未加密」，看起來只要比照身分證套用 AES-GCM 即可。

**實作前的查證改變了做法**：該欄位被 DBR 計算使用，每筆清單查詢都要讀。
加密會讓熱路徑多 N 次解密，且 SQL 層無法再以收入篩選或排序。
再查前端後發現真正的缺陷是「原值被回傳到所有 API 回應，但沒有任何 UI 顯示它」——
問題是**曝露面**，不是儲存方式。

**規則**：處理敏感欄位前先問兩件事：
1. 誰在讀它？（顯示用 → 可加密；計算用 → 加密會付出持續成本）
2. 回傳它的端點真的需要它嗎？（多數情況下移除欄位比加密更有效且更便宜）

「最小化揭露」通常比「加密後照樣全量回傳」更能降低風險。
儲存層加密防的是資料庫外洩；不回傳防的是 API 誤用與日誌洩漏，兩者的威脅模型不同。

## 2026-09-23 500 回應必須在伺服器端留下真因

**失敗模式**：核准端點回 `{"error":"failed to create funding listing"}`，
但伺服器端沒有任何紀錄。我花了數輪猜測（SQL 語法？欄位缺失？migration 順序？）
並逐一以 psql 手動驗證，才想到要先把真因記下來。

加上結構化錯誤日誌後，同一個問題一行就定位：
`unable to encode 14 into text format for text (OID 25)`。

**預防規則**：對客戶端回傳通用訊息是對的（不洩漏內部細節），
但**同時**要把原始錯誤寫進伺服器日誌。兩者並不衝突。
已新增 `writeInternalError(w, message, cause)` 供 500 路徑使用。

**排查順序的教訓**：遇到不明的 500，第一步應該是「讓錯誤可見」，
而不是憑對程式碼的印象逐一試錯。

## 2026-09-23 pgx 參數不可放進 SQL 字串拼接

**失敗模式**：`NOW() + ($12 || ' days')::interval` 讓 pgx 把 `$12` 推論為 text，
而 Go 傳的是 `int`，於是編碼失敗（`cannot find encode plan`）。

**預防規則**：需要以參數構造 interval 時用乘法而非字串拼接：
`$12::int * INTERVAL '1 day'`。
更一般的原則是——參數的型別由它在 SQL 中的使用位置決定，
把參數放進字串運算會讓它被推論為字串。

## 2026-09-23 加 NOT NULL 欄位要同時檢查 seed

**失敗模式**：migration 009 為 `listings` 加上 NOT NULL 的 `funding_deadline`，
但 seed 的 INSERT 沒有這個欄位，部署時 seed 失敗。

**預防規則**：`ALTER TABLE ... ADD COLUMN ... NOT NULL` 之後，
必須檢查所有寫入該表的地方——包含 seed、測試 fixture、以及其他 migration。
`grep -rn "INSERT INTO <table>"` 是最快的確認方式。

## 2026-09-23 手動測試留下的資料會污染後續斷言

**失敗模式**：我為了驗證 OCR 比對，手動建了一筆 `applicantName = "A123456789"` 的申請
（讓姓名與測試圖片中的文字相符）。這筆資料留在 develop 資料庫裡，
之後端到端的「回應不得含完整身分證」斷言就掃到了這個字串並報錯。

程式沒有問題——身分證欄位仍正確遮罩為 `A12****789`。是我的測試資料讓斷言誤報。

**預防規則**：手動驗證時如果要塞入「看起來像敏感資料」的值，
用明顯的測試標記（`TEST-NAME-001`）而不是真實格式的字串。
若必須用真實格式，驗證完立刻清掉。

**附帶觀察**：這次誤報反而證明那條斷言是有效的——它真的會抓到回應中的明文身分證。
誤報不等於斷言沒用；查清原因比直接放寬斷言重要。

## 2026-09-23 OCR 這類「智慧」功能要先界定能力邊界

**情境**：待辦寫「OCR 自動驗證文件內容」。這個描述很容易做成過度承諾的樣子——
看起來像在驗證文件真偽，實際上 OCR 只能讀出文字，完全無法辨識變造。

**做法**：實作前先在計畫中明確寫下**不做**什麼（不判斷真偽、不自動核准、
不做版面理解），只做可驗證的事（比對申請人填寫的值是否出現在文件中）。
前端與文件都標示「僅供參考，不判斷真偽」。

**規則**：涉及辨識、推論、評分的功能，規格要先寫清楚「這個功能不能回答什麼問題」。
否則使用者（與未來的自己）會以為它提供了它給不了的保證——
在授信這種場景，誤信自動驗證的後果比沒有這個功能更糟。

**連帶設計**：三態結果（matched / not_found / unreadable）比二態誠實。
把「影像模糊讀不出來」和「內容確實不符」混為一談會直接誤導風控判斷。

## 2026-09-23 CSRF 保護不可套用在「尚未登入」的端點

**失敗模式**：我把 `forgot-password`、`reset-password`、`verify-email` 都納入 CSRF 保護，
結果 forgot-password 直接回 403。原因很直接——**呼叫這個端點的人正是無法登入的人**，
他們沒有 session、也沒有 CSRF token。後兩者同理：使用者是從信件連結進來的。

**預防規則**：加 CSRF 保護前先問「呼叫這個端點的人有 session 嗎？」
沒有 session 的流程（登入、註冊、忘記密碼、信件連結）必須豁免，
它們的防護要來自別處：高熵且單次使用的 token、限流、不洩漏帳號存在性。

**一般化**：安全機制的適用前提要跟著機制本身一起想。
CSRF 防的是「借用受害者的既有 session」，沒有 session 就沒有這個攻擊面。

## 2026-09-23 「需要外部服務」不等於無法驗證

**情境**：email 驗證與密碼重設先前被我列為「需要郵件服務」的已知限制而跳過。

**實際做法**：MailHog 提供 SMTP sink 加 HTTP API，於 develop 的 compose 啟動後，
端到端測試可以真的收信、用正規表示式解析出連結中的 token、走完整個流程。
結果是 17 項真實斷言，而不是「寫了介面並假設它會動」。

**規則**：把功能標為「需要外部服務」之前，先找有沒有可在本機跑的替代端
（郵件→MailHog、物件儲存→MinIO、金流→sandbox）。
分辨「真的需要商業合約」（如真實金流結算）與「只是需要一個收件端」很重要——
後者通常有現成的本機方案，跳過它會少掉真正能證明功能可用的驗證。

## 2026-09-23 鎖定機制本身可能成為 DoS 工具

**設計陷阱**：登入失敗鎖定的直覺做法是「N 次失敗後鎖定帳號」。
但若鎖定是永久的（或需要管理員解鎖），攻擊者只要對任意帳號故意輸錯 N 次，
就能讓該使用者無法登入——防護本身變成了攻擊工具。

**採取的做法**：
1. 暫時鎖定且時長遞增（5 分鐘 → 30 分鐘 → 2 小時），並設 24 小時上限
2. 提供合法的自救管道：密碼重設成功即解除鎖定
3. 成功登入清空計數，避免長期累積

**另一個要點**：鎖定回應不可洩漏帳號是否存在。
若只有存在的帳號會回 429，那個回應本身就是帳號存在的證據。
本實作對不存在的帳號永遠回 401（沒有紀錄可累加），且達門檻前兩者的
狀態碼與回應主體完全相同。

**一般化**：任何「觸發後限制使用者」的防護都要問：
攻擊者能不能故意觸發它來傷害別人？如果能，就需要自救管道與時效上限。
